TB BUGS FOUND AND FIXED DURING THIS SESSION (TB-side, not RTL — per the
verify agent's own tests, fixed directly; documented for transparency)
------------------------------------------------------------------------
1. UART monitor (tb_common/uart_monitor.vh): an early version synchronized
   frame starts with `@(negedge uart_tx)` then counted bit-windows with
   `@(posedge clk)` — mixing an edge-type wait on a non-clock net with
   clock-edge counting produced a spurious extra sampled cycle at every
   frame boundary (confirmed a TB artifact, not an RTL bug, by cross-
   checking against a plain `@(posedge clk)`-only polling monitor reading
   `dut.u_uart_tx.{state,baud_cnt}` directly — the real pin holds each
   symbol for exactly CLK_DIV cycles). Rewritten to poll purely via
   `@(posedge clk)`, eliminating the cross-event-region race.
2. tb_mac_datapath_unit.v / tb_uart_line_fmt_unit.v: stimulus tasks used
   BLOCKING assignment to clear a control signal (`mac_bias_ld`, `lf_start`)
   immediately after the `@(posedge clk)` it needed to be seen HIGH on —
   racing against the DUT's own NBA-driven always block for that same edge
   (process scheduling order between separate always/initial blocks on the
   same edge is not guaranteed). Fixed by switching to NON-BLOCKING
   assignment throughout (matching tb_common/clk_rst.vh's `tb_reset`
   pattern, which already did this correctly).
3. tb_reset.v: reading DUT-internal registers immediately after
   `@(posedge clk)` (no settle delay) intermittently raced against the
   DUT's own always blocks for that same edge — confirmed via `$strobe`
   (which defers to the fully-settled value) showing a DIFFERENT value than
   a same-instant `$display`. Fixed with a `#1` settle delay before every
   post-edge DUT-signal read (also added defensively to tb_mnist_top.v's
   equivalent reads, which had happened to work without it — the DUT
   signals sampled there are stable well before the sampling point, but the
   fix removes the fragility rather than relying on that).
4. tb_mnist_top.v: the concurrent UART-capture process was still mid-byte
   on the 200th (last) image's line when the main process reached its loop
   end and called $finish, truncating the last line (199/200 lines
   captured). Fixed by waiting a worst-case-line-length margin
   (`69*10*CLK_DIV+200` cycles) after the main loop before finishing.
5. tb_mnist_top.v: the HOLD-window led[11]-constancy check flagged the
   expected transition edge itself (led[11] snapping to 0 the SAME cycle
   `lc_busy` deasserts is REQ-019/020's own specified behaviour, not a
   violation) as a false FAIL. Fixed to only flag toggles strictly INSIDE
   the hold window (excluding the boundary edge).
6. test_mnist_top.py (cocotb): see the Stage 2 write-up above — a
   sequential "wait for HOLD right after UART decode" assumption was wrong
   given `lf_done`'s accept-vs-complete semantics; replaced with a
   concurrent monitor coroutine.

None of these were RTL issues — each was independently confirmed against
either a from-scratch cross-check tool (a second, minimal `@(posedge
clk)`-only Verilog probe) or Stage 1 vs Stage 2 agreement (two independent
implementations reaching the same PASS verdict on the same design once the
TB bugs were fixed).

FINDINGS
--------
See verify/FINDINGS.md for full detail. Summary:

**FINDING-001 (RTL, Low severity):** `led[0]` reads 1 (not 0) throughout
reset, violating REQ-030 / VP-TOP-001's literal "led[11:0]==0 ... throughout
reset" criterion, and contradicting arch.md's own documented reset-behaviour
claim for BLK-010. Root cause: `led_ctrl.v` resets `verdict_r<=2'd0`
(CORRECT), not `2'd2` (TRASH) — the only encoding that forces
`led_digit=(verdict_r==2'd2)?0:(10'd1<<pred_r)` to all-zero; combined with
`pred_r<=4'd0`, `led_digit` evaluates to `10'd1<<0=1`. Cosmetic/display-only:
does NOT affect the inference data path (fully bit-exact, 0 mismatches
across 209 total images verified between both stages) — only the LED
digit-display's transient value between reset-release and the first result
being presented (~510 us at default hardware pacing). Reproduction command
and suggested one-line fix direction (reset `verdict_r` to `2'd2` instead of
`2'd0`) are in FINDINGS.md. NOT applied — rtl/ is frozen for this
verification pass.
